\chapter{Project Work Status}

This chapter documents the current status of the SiteX project, summarizing the work completed across both the 7th and 8th semesters. It traces the project's evolution from a tabular machine-learning baseline to a fully graph-neural-network-driven location intelligence platform. The chapter is organized into three parts: work completed in the 7th semester (stable foundation), work completed and ongoing in the 8th semester (GNN transition), and the expected outcomes of the remaining work.

\subsection{Expanded Data Collection Campaign (\textasciitilde{}1 Week)}
The single largest effort of the 8th semester was a large-scale, multi-day scraping campaign to build a dataset of sufficient size and richness for GNN training. The previous 7th-semester dataset was too small and lacked individual review text and foot traffic data.

\paragraph{Scraping Infrastructure.}
The team adopted the open-source \textbf{\texttt{google\allowbreak-maps\allowbreak-scraper}} tool (\url{https://github.com/gosom/google-maps-scraper}), a Go-based CLI application that scrapes Google Maps business data in bulk. The decision to switch from a browser-based approach was made because this tool:
\begin{itemize}
    \item Supports bulk keyword and geographic bounding-box queries.
    \item Outputs structured JSON/CSV data including reviews, ratings, popular times, price tier, and operating hours.
    \item Can be run headlessly on a server or local machine without a browser.
\end{itemize}

\paragraph{Scraping Timeline (approx.\ 7 days).}
\begin{itemize}
    \item \textbf{Day 1--2: Configuration and Pilot Runs.} The tool was installed, configured with the target study area bounding box (Kathmandu Valley + Bhaktapur district), and pilot runs were executed to validate the output schema and estimate collection time per batch.
    \item \textbf{Day 3--5: Cafe and Competitor Data Collection.} Sequential scraping batches were run targeting cafes, restaurants, and food-service competitors. Each batch required monitoring for rate-limiting and retry logic. Multiple runs were needed to cover the full geographic extent.
    \item \textbf{Day 6--7: POI Category Collection.} Separate scraping jobs were run for each POI category: banks, education institutions, health facilities, temples, and other amenities.
\end{itemize}

\paragraph{Dataset Scale Achieved.}
\begin{itemize}
    \item \textbf{$\sim$10,000} cafe and competitor business records with full metadata (used as training nodes).
    \item \textbf{$\sim$30,000} Points of Interest (POIs) across five categories.
    \item Per cafe: individual review texts, per-review star ratings, popular times (hour-by-hour foot traffic), price tier, and operating hours.
\end{itemize}

\subsection{Dataset Cleaning and Deduplication}
Raw data from multiple scraping batches required significant cleaning before use:
\begin{itemize}
    \item \textbf{Deduplication:} Multiple scraping runs with overlapping bounding boxes produced duplicate records. A deduplication pass using Google Place ID as the unique key was applied to remove duplicates.
    \item \textbf{Coordinate Validation:} Records with missing, null, or out-of-bounds latitude/longitude coordinates were filtered out.
    \item \textbf{Review Filtering:} Reviews in languages other than English and Nepali were detected and flagged. Reviews with fewer than three words were excluded from sentiment analysis.
    \item \textbf{Handling Missing Fields:} Records with missing foot traffic data or rating data were retained but flagged; missing values were imputed with the dataset median during feature construction.
    \item \textbf{Output:} A clean, deduplicated dataset stored as structured CSV and imported into the SpatiaLite database.
\end{itemize}

\subsection{Sentiment Analysis Pipeline}
Given access to individual review texts, a complete NLP pipeline was built to produce a per-cafe sentiment score:

\begin{itemize}
    \item \textbf{Model Selection:} A pre-trained transformer-based sentiment model was used to score each individual review on a continuous sentiment scale.
    \item \textbf{Batch Inference:} Reviews were processed in batches to manage memory usage during inference across the full review corpus.
    \item \textbf{Score Aggregation:} Individual review-level sentiment scores were aggregated per cafe by taking a weighted mean, assigning higher weight to more recent reviews to reflect current business sentiment.
    \item \textbf{Output:} A \texttt{sentiment\_score} column was computed and appended to the cafe dataset. This field directly participates in the ground truth composite score.
\end{itemize}

\subsection{POI Weight/Scoring Redesign}
The original POI scoring scheme (which used manually assigned static weights per category) was replaced with a data-driven approach consistent with the GNN philosophy:
\begin{itemize}
    \item \textbf{Old approach:} Hand-crafted static weights per category type (e.g., banks $\times$ 0.3, health $\times$ 0.5) used to compute a tabular ``influence score'' for each location.
    \item \textbf{New approach:} POI nodes in the graph carry their own feature vectors (including rating, review count, and category encoding). The HeteroGAT model learns the effective importance of each POI type through attention weights during training, rather than using pre-specified weights.
    \item \textbf{Road graph retention:} The OSMnx road-network distance is still used as a continuous edge attribute (reflecting real travel distance), but the model now learns how to use this distance contextually rather than applying a fixed exponential decay formula.
\end{itemize}

\subsection{Ground Truth Composite Score Redesign}
The target variable for supervised training was completely redesigned to be based solely on intrinsic business success signals, deliberately decoupling it from spatial features:

\begin{equation}
S_i = w_1 \cdot \text{rating}_i + w_2 \cdot \log(1 + \text{count}_i) + w_3 \cdot \text{sentiment}_i + w_4 \cdot \text{traffic}_i
\end{equation}
\begin{equation}
y_i = 100 \times \frac{S_i - \min(S)}{\max(S) - \min(S)}
\end{equation}

Key design decisions:
\begin{itemize}
    \item \textbf{Log-scaled review count} ($\log(1+\text{count})$): Dampens the effect of viral outliers with tens of thousands of reviews.
    \item \textbf{Exclusion of road/spatial features from the target:} The ground truth score contains no distance or POI-density information. This forces the GNN to learn spatial influence purely from the graph message-passing structure.
    \item \textbf{Min-max normalization to 0--100:} Produces a bounded, interpretable suitability score for display in the UI.
\end{itemize}

\subsection{Database Migration --- CSV to SpatiaLite}
To simplify deployment, eliminate external database server dependencies, and optimize runtime query speed, the spatial data store was migrated:
\begin{itemize}
    \item \textbf{From:} Structured CSV files (the raw and cleaned output of the data collection and sentiment analysis pipeline).
    \item \textbf{To:} \textbf{SpatiaLite} --- a self-contained, file-based spatial database (an extension of SQLite with spatial functions via libspatialite).
    \item \textbf{Schema mapping:} All four core datasets (\texttt{listings}, \texttt{competitors}, \texttt{points\_of\_interest}, and \texttt{demographics}) were structured, imported, and spatialized with R-tree spatial indexing.
    \item \textbf{Backend update:} The FastAPI backend was updated to use \textbf{aiosqlite} for asynchronous SpatiaLite queries, replacing the previous in-memory GeoPandas and BallTree spatial search approach.
    \item \textbf{Deployment benefit:} The entire data layer is now a single portable \texttt{.db} file. No database server needs to be running for the application to function.
\end{itemize}

\subsection{OSMnx Road Graph Setup and Serialization}
The road network graph required for road-aware distance computation was set up as a persistent backend asset:
\begin{itemize}
    \item \textbf{Graph download:} The road network for the Kathmandu and Bhaktapur districts was downloaded from OpenStreetMap using the OSMnx Python library.
    \item \textbf{Graph cleaning:} OSMnx's built-in simplification and consolidation routines were applied to remove isolated nodes, duplicate edges, and self-loops.
    \item \textbf{Serialization:} The cleaned graph was serialized using Python's \texttt{pickle} module and saved as \texttt{road\_graph.pkl}. This avoids re-downloading and re-processing the graph on every server restart.
    \item \textbf{Runtime loading:} The backend loads \texttt{road\_graph.pkl} once at startup and keeps it in memory. Shortest-path distances are computed on demand using NetworkX's shortest-path algorithms, replacing the previous live OSMnx API calls.
\end{itemize}

\subsection{Task 8: Heterogeneous Graph Construction Pipeline}
A full graph construction pipeline was implemented to transform the SpatiaLite database into a PyTorch Geometric \texttt{HeteroData} object suitable for HeteroGAT training:
\begin{itemize}
    \item \textbf{Node featurization:} Cafe nodes receive feature vectors of (normalized rating, log-review count, sentiment score, price tier). POI nodes receive (category one-hot encoding, rating, review count). Competitor nodes receive (rating, review count, estimated category).
    \item \textbf{Edge construction:} For each candidate-to-POI and candidate-to-competitor pair within the search radius, a directed typed edge is created. The road-network shortest-path distance is attached as a scalar edge attribute.
    \item \textbf{Graph assembly:} The assembled \texttt{HeteroData} object is validated for schema consistency (node feature dimensions, edge index bounds) before being passed to the training loop.
\end{itemize}

\section{Remaining Works and Expected Outcomes}
% =============================================================

The following work is underway and constitutes the primary remaining effort for the 8th semester defense:

\begin{itemize}
    \item \textbf{HeteroGAT Training and Evaluation:} Finalize model training and evaluate its performance against the XGBoost baseline. Expected outcomes include lower error rates, improved spatial generalization, and graph-native interpretability via attention weights.
    \item \textbf{Enhanced Interpretability Layer:} Upgrade the UI Explanation tab to provide a dual-layer explanation: data-level (top contributing POIs) and model-level (HeteroGAT attention weights).
    \item \textbf{Personalized Business Input:} Allow users to define their café or restaurant profile, including business type, target customer segment, budget constraints, and space requirements to generate customized suitability assessments.
    \item \textbf{Real-Time Data Integration:} Incorporate real-time foot traffic and mobility data from sources like mobile location services to provide dynamic location assessments.
    \item \textbf{Expanded Economic Indicators:} Integrate economic data such as rental price trends and purchasing power analysis to enhance the model's understanding of location viability.
    \item \textbf{Multi-Branch Optimization:} Develop features that allow franchise owners to plan and optimize multiple outlet locations simultaneously.
    \item \textbf{Café Categorization and Characterization:} Develop a classification framework categorizing cafés based on ambiance, cuisine type, and price range to deliver context-aware assessments.
    \item \textbf{Prescriptive Location Recommendations:} Move beyond evaluating a single point to actively prescribing optimal locations based on the type of café the user intends to open.
\end{itemize}
